## 2. 本次调整结论

本次文档基于当前 MVP、已有方案文档和人工备注调整，先形成可确认的后续规划，不直接进入开发。

重点调整：

1. 继续保持开源通用抽象，不把任何专有行业、组织、平台或内部系统概念写入核心设计。
2. 明确当前 MVP 只有 `mock`、`http`、`local_function`、`ui_handoff` 四类默认 Invoker。
3. 明确 `workflow`、`provider_platform` 是 Agent 类型预留，不是当前默认可执行 Invoker。
4. 明确聊天类子智能体应作为可配置 Agent / Intent 进入 Agent Registry，但当前不新增独立聊天 Invoker。
5. 明确目标 Agent 以路由前候选筛选为主，后续规划不把“路由后目标校验”作为单独业务功能项。
6. 暂时取消不清晰的 v0.5 RAG 插件示例规划，后续等 Knowledge Source 边界确认后再规划。
7. 前端测试台改造只写成设计需求：中间模拟正常聊天窗口，展示中控返回给用户的回答；右侧统一展示计划、路由意图、Evidence、调用结果和调试状态。
8. 版本规划改为按模块拆分，便于逐个模块设计、开发、测试和验收；场景级筛选仅作为可扩展能力记录，暂不作为开发要求。
9. 修正路由动作全集、`decision.message` 阶段性口径和 `show_plan` 兼容迁移要求，避免后续开发误读协议。
10. 补充 Evidence 检索预算、记忆提取策略、Plan 部分失败处理、评估口径和数据安全边界。
11. 明确用户可见回答的统一演进路径：M1 用 `decision.message` 过渡，M3 新增统一的 `assistant_message`，并收窄其他 message 字段职责。

## 3. 项目定位

`open-intent-router` 是一个面向多 Agent / Tool / Workflow 应用的通用意图识别与中控编排后端。

它负责接收宿主应用传入的自然语言请求，结合用户、会话、场景、候选能力、上下文、记忆和证据，输出结构化路由决策、澄清问题、执行计划或 Host 协作指令。

本项目不是某个具体业务系统，也不是完整知识库平台、低代码平台、Bot 平台或工作流引擎。核心仓库必须保持开源形态，行业或组织内部接入通过配置、插件、Adapter 和宿主应用扩展完成。

## 4. 设计原则

### 4.1 通用抽象优先

核心仓库不使用专有业务名词作为一等概念。涉及内部系统、行业场景或私有平台时，只能通过通用抽象承载。

| 专有表达类型 | 核心通用抽象 |
| --- | --- |
| 专有主体记忆 | User Memory、Subject Memory、Profile Memory |
| 内部业务知识库 | Knowledge Source、Evidence Provider |
| 专有流程或话术模板 | Playbook、Script、Workflow Template |
| 特定业务角色 | Operator、End User、Host User |
| 内部系统页面 | Host App UI、UI Handoff |
| 业务标签 | Role、Group、Tenant、Attribute、Access Policy |

### 4.2 核心与宿主应用分层

核心项目负责：

1. Agent / Tool / Workflow 的通用定义。
2. 用户、会话、事件、计划和运行结果的通用协议。
3. 意图识别、候选裁剪和结构化路由。
4. 上下文选择、证据注入、记忆检索和预算控制。
5. 可后端执行能力的基础调用。
6. 路由、计划、执行和调试日志。

宿主应用负责：

1. 真实用户身份、组织权限和业务权限来源。
2. 私有业务数据、知识库、文件、剧本和策略。
3. 私有 Agent 平台、页面跳转和执行环境。
4. 私有 prompt、术语解释和业务约束。
5. 生产环境密钥、审计策略和数据生命周期管理。

### 4.3 先做可确认设计，再做开发

后续每个模块进入开发前，都应先确认：

1. 这个能力是否属于通用中控核心。
2. 是否可以通过 schema、配置、插件或 Adapter 表达。
3. 是否会泄漏某个宿主系统或行业的专有概念。
4. 是否能被独立测试和回归验证。
5. 是否能在前端测试台中被观察和解释。

## 5. 当前 MVP 能力基线

当前 MVP 已具备：

1. FastAPI 后端服务。
2. 通用 Agent Definition Schema。
3. 文件、数据库、混合模式的 Agent Registry。
4. OpenAI-compatible LLM Client 和 Mock LLM。
5. 默认 Invoker：`mock`、`http`、`local_function`、`ui_handoff`。
6. 基础路由接口：`route`、`route-and-invoke`、`route-and-execute`。
7. 会话消息、Agent Event、Agent Run / Result、Plan 和 Route Log。
8. PlanExecutor、`execution_policy` 和 `next_action`。
9. Evidence Provider 插件接口和文件型固定问题命中。
10. 本地可视化测试 UI。

当前 MVP 尚未充分覆盖：

1. 场景级能力空间建模。
2. 用户级、会话级、任务级记忆管理。
3. 上下文预算、裁剪、摘要和压缩。
4. 多知识源动态选择和 Evidence 调度。
5. 路由质量评估、样例集和回归测试。
6. 面向正常聊天体验的测试台布局。

## 6. 当前 Invoker 与聊天类 Agent 边界

### 6.1 默认 Invoker

当前默认后端 Invoker 只有四类：

| Invoker | 当前用途 |
| --- | --- |
| `mock` | 本地开发、测试和示例 Agent |
| `http` | 调用外部 HTTP API |
| `local_function` | 调用进程内受信任函数 |
| `ui_handoff` | 返回宿主应用需要打开的页面或交互信息 |

`workflow` 和 `provider_platform` 已在 Agent 类型中预留，但当前没有默认 Invoker。后续如果接入工作流引擎、第三方 Agent 平台或长任务平台，应作为独立 Adapter 设计，不直接污染核心调用协议。

### 6.2 聊天类子智能体

聊天类子智能体应作为可配置 Agent / Intent 进入 Agent Registry。也就是说，聊天类子智能体和工具类 Agent 一样，都需要配置 `agent_id`、`name`、`description`、`capabilities`、`trigger`、`required_inputs`、`access_policy`、`invocation` 和可选 `ui_handoff`。

区别在于：聊天类子智能体通常不是一次性后端函数调用，而是由宿主应用或外部 Agent 平台承载持续对话。当前核心项目不新增一个单独的 `chat_agent` Invoker，而是用现有通用字段表达：

| 配置项 | 建议用法 |
| --- | --- |
| `type` | 使用 `ui_handoff` 表示由宿主应用打开聊天界面；或使用 `provider_platform` 预留给后续平台 Adapter |
| `description` / `capabilities` | 描述该聊天 Agent 能处理的意图范围 |
| `trigger` | 配置关键词、正例和反例，用于意图识别 |
| `required_inputs` | 配置进入该聊天 Agent 前必须补齐的信息 |
| `ui_handoff` | 配置宿主应用需要打开的聊天页面、窗口或路由 |
| `metadata` | 保存聊天 Agent 的模式、外部平台标识、会话策略等扩展信息 |

推荐 metadata 模板的作用不是新增核心字段，而是给聊天类 Agent 的扩展配置提供稳定约定，方便文档示例、测试台表单、后续 Adapter 和私有接入方使用同一套 key。它可以减少不同接入方各写各的 metadata，避免后续适配器难以解析。

示例用途：

1. 标记 Agent 是聊天型还是一次性任务型。
2. 记录外部平台或宿主应用中的 Agent 标识。
3. 记录会话策略，例如是否复用 `agent_session_id`。
4. 记录打开聊天界面时需要的宿主应用参数。
5. 为后续 `provider_platform` Adapter 预留解析约定。

推荐模板只作为文档和示例约定，M1/M3 阶段不要求核心 schema 增加新字段。

现有运行模型是：

1. 用户在主入口发起请求，`source=host_chat`。
2. 路由器识别为打开某个 Agent，返回 `open_agent` 或 `ui_handoff`。
3. 宿主应用打开对应 Agent 页面、窗口或聊天环境。
4. 用户在该 Agent 内继续输入时，请求使用 `source=agent_chat`，并传入 `current_agent.agent_id`。
5. 如果存在外部 Agent 会话，可通过 `current_agent.agent_session_id` 传递。
6. 中控根据当前 Agent、Agent 历史和用户输入判断 `continue_agent`、`open_agent`、`exit_agent` 或新任务。
7. 子 Agent 执行进度和结果通过 Agent Event 或 Run Result 回流。

因此，聊天类子智能体要作为可配置意图进入中控，但当前项目不负责托管一个持续运行的聊天 Agent 进程；它负责识别是否进入、继续、切换或退出该聊天 Agent，以及如何把相关上下文交给宿主应用或后续 Adapter。

### 6.3 路由动作全集与退出切换

路由决策动作以 `app/schemas/common.py` 中 `RouteAction` 为权威定义，全文其他章节不得各自裁剪子集。退出和切换只是动作全集中的一部分。

| 动作 | 含义 |
| --- | --- |
| `reply` | 无需调用 Agent，由路由器直接回复用户 |
| `clarify` | 缺少必要信息，需要追问 |
| `open_agent` | 打开或切换到目标 Agent |
| `continue_agent` | 继续当前 Agent（`target_agent_id` 必须等于 `current_agent_id`） |
| `exit_agent` | 退出当前 Agent 上下文 |
| `show_plan` | 兼容动作；新客户端应优先看 `plan` 是否存在 |
| `unsupported` | 没有合适 Agent 或请求不被支持 |
| `silent` | 无需回复 |

## 7. 下一阶段能力模型

后续能力按模块划分，避免用一个大版本混合多个目标。每个模块都应有独立设计、任务、测试和验收口径。

模块划分：

1. M1：测试台聊天体验与状态面板。
2. M2：场景与能力空间建模。
3. M3：意图识别、多意图拆解和槽位澄清。
4. M4：上下文预算与 Context Pack。
5. M5：用户级、会话级、任务级记忆。
6. M6：Knowledge Source 与 Evidence 调度。
7. M7：Plan 编排与执行协作增强。
8. M8：可观测性、评估与回放。

核心主流程：

```text
User Input
  -> Candidate Agent Pre-filter
  -> Memory Retrieval
  -> Evidence Retrieval
  -> Context Pack Builder
  -> Intent Router
  -> Decision / Plan / NextAction
  -> Invocation / Host Handoff / Clarification
  -> Event + Result + Memory Update
```

场景级筛选属于可扩展流程，后续可插入到 Candidate Agent Pre-filter 之前或之中，但当前不作为开发要求。

## 8. M1：测试台聊天体验与状态面板

### 8.1 目标

把当前中间的“第几轮对话卡片”改造为更接近真实用户使用的聊天窗口。中间只承载对话交互本身，右侧统一承载路由、计划、证据、调用和调试状态。

本模块只改变测试台体验，不改变后端路由协议。

### 8.2 `decision.message` 现状

当前 `decision.message` 是 `RouteDecision` 中的字符串字段，用于承载路由器返回给客户端的可展示文案。现有 Prompt 只约束它为 `string`，并未把它单独命名为 `assistant_message`。当前前端也已经把它作为路由结果中的提示文案展示。

相关字段和常见文案来源包括：

1. LLM 路由输出的 `decision.message`。
2. Mock LLM 返回的路由提示，例如 “Routing to Summarizer.”。
3. 多意图兜底计划文案，例如“已生成多步骤执行计划。”。
4. 计划确认等协作提示可能出现在 `next_action.message`，例如“请确认是否执行该计划。”；该字段属于右侧 Plan 状态展示，不作为 M1 助手气泡来源。

M1 阶段先不新增后端字段，聊天窗口中的助手气泡固定使用中控当前返回给客户端的可展示文案，即 `decision.message`。M3 阶段需要按 §10.3 的统一用户可见回答需求新增 `assistant_message`，将聊天区展示入口从 `decision.message` 迁移到 `assistant_message`。

### 8.3 当前问题

当前对话区按“第 1 轮、第 2 轮”展示，每轮卡片里混合了用户输入、路由动作、目标 Agent、调用结果等信息。这对开发调试有用，但不像真实聊天产品。

问题：

1. 用户对话和调试状态混在一起。
2. Plan、Evidence、Invocation、RouteResponse 分散在多个面板中。
3. 不利于模拟真实 Host Chat 的交互体验。
4. 后续加入 Context Pack、Memory、Knowledge 后，中间区域会更拥挤。

### 8.4 目标交互

中间聊天窗口：

1. 只展示用户消息和系统/助手响应气泡。
2. 不展示“第几轮”的文案。
3. 每次发送后在聊天区追加用户输入。
4. 路由完成后追加中控当前返回给用户的回答，M1 固定使用 `decision.message`；M3 后聊天区改为只消费 `assistant_message`，Agent 调用结果先统一放在右侧状态面板中展示，是否组合进 `assistant_message` 由后端协议统一决定。
5. 支持正常聊天输入框、发送按钮、新会话按钮。
6. 高级上下文配置继续保留，但不抢占聊天主体。

右侧状态面板：

右侧状态面板需要使用 Tab 分组：

1. Route：默认优先展示，包含 `decision.action`、`target_agent_id`、置信度、原因、候选 Agent。
2. Plan：默认优先展示，包含步骤、状态、执行策略、`next_action`、确认/继续/恢复/取消。
3. Context：后续模块接入后展示 Context Pack、预算使用和裁剪原因。
4. Memory：后续模块接入后展示本次召回、写入、可查看和可修改的记忆。
5. Evidence：固定问命中、知识证据、候选 Agent 提示信息。
6. Debug：调用预览、调用结果、UI Handoff、完整 RouteResponse、Plan、Run、Event 响应。

### 8.5 功能需求

1. 新增聊天式消息模型，区分 `user`、`assistant`、`system`。
2. 对话区只渲染聊天气泡和输入区。
3. 移除或隐藏“第 N 轮”展示方式。
4. 中控返回给用户的回答转换为助手气泡。
5. 右侧增加统一状态面板，按 Route、Plan、Context、Memory、Evidence、Debug 分 Tab。
6. Plan 操作按钮只出现在右侧状态区。
7. Event JSON 提交保留在右侧调试区。
8. 保留完整 JSON 调试能力，但默认折叠。
9. 右侧默认先展示 Route 和 Plan；其他状态按需切换。

### 8.6 测试重点

1. 首次进入页面时聊天窗口为空态正常。
2. 发送 route-only 请求后，中间出现用户气泡和中控回答气泡。
3. 发送 route-and-invoke 请求后，调用结果不挤入聊天卡片，而是在右侧展示。
4. 当响应包含 Plan 时，右侧 Plan 面板出现。
5. 当响应包含 Evidence 时，右侧 Evidence 面板出现。
6. 新会话会清空聊天区和右侧状态。

## 9. M2：场景与能力空间建模

### 9.1 目标

场景与能力空间建模是后续可扩展能力，用于让中控知道当前请求处在哪类通用场景、可用哪些 Agent、应使用哪些上下文和知识源，避免所有能力都进入同一次路由。

本模块当前只作为规划记录，不作为近期开发要求。

### 9.2 通用概念

| 概念 | 说明 |
| --- | --- |
| Scenario | 宿主应用中的任务场景，例如工作台助手、内容生成、客服辅助、流程办理 |
| Capability Space | 某个场景下可用的 Agent、Tool、Workflow 集合 |
| Scenario Policy | 场景内的上下文优先级、知识源选择和执行策略 |
| Entry Channel | 用户从聊天框、页面按钮、侧边栏、Webhook 等入口发起请求 |

### 9.3 功能需求

1. 支持在请求上下文中传入 `scenario_id`、`channel`、`page_context`。
2. 支持按场景筛选候选 Agent。
3. 支持场景级默认执行策略。
4. 支持场景级上下文预算和知识源范围。
5. 支持场景级 prompt overlay，但作为配置注入，不写死在核心 prompt。
6. 近期不要求实现，仅作为后续扩展项保留。

### 9.4 测试重点

1. 不同 `scenario_id` 下候选 Agent 不同。
2. 场景不可用的 Agent 不进入 LLM 候选列表。
3. 场景默认执行策略能影响 Plan 的 `execution_policy`。
4. 未传场景时保持现有兼容行为。

## 10. M3：意图识别、多意图拆解和槽位澄清

### 10.1 目标

提升中控对自然语言的理解能力，使其能处理单意图、多意图、继续当前任务、切换 Agent、退出 Agent、追问、省略和引用历史结果。

### 10.2 候选 Agent 策略

目标 Agent 应在输入判断意图前就完成候选筛选。路由器只能把当前用户可用的候选 Agent 传给 LLM；如果未来启用场景策略，再叠加场景级候选过滤。

当前开发重点放在路由前筛选。筛选顺序固定为：权限过滤 > 强确定性规则 > 语义/标签筛选 > LLM 判断。首版标签/语义筛选只作为召回观察信号，不裁剪候选 Agent；基础权限过滤是安全硬边界。

1. 先根据 `enabled`、`access_policy`、用户角色、用户组、租户和属性做可用性过滤。
2. 固定问强命中在权限过滤之后执行；目标 Agent 可用时直接强路由，不再调用 LLM。
3. 固定问强命中但目标 Agent 不可用时返回无权限提示，不进入 LLM 兜底判断。
4. 再根据 Agent / Intent 标签计算召回观察信号，标签可来自 Agent 配置、trigger、capabilities 或 metadata 中的统一约定字段。
5. 标签命中和无命中只写入 `context.metadata`，不裁剪传给 Evidence Provider 和 LLM 的候选集。
6. Evidence Provider 的弱候选提示只进入上下文，不缩小 LLM 候选集。
7. 聊天类子智能体同样作为候选 Agent 参与筛选和意图判断。

正确模型是：

```text
Registry + Access Policy
 -> available_agent_ids
  -> Strong fixed-question route within access boundary
  -> Tag / semantic observe-only signals
  -> LLM route within available_agent_ids
```

基础 schema 校验仍可保留为系统防线，但不作为后续模块的业务开发重点。

### 10.3 功能需求

1. 支持识别全集动作 `reply`、`clarify`、`open_agent`、`continue_agent`、`exit_agent`、`show_plan`、`unsupported`、`silent`（以 §6.3 为准）。
2. 支持多意图生成 Plan。
3. 支持从输入、历史消息、最近结果、事件和记忆中提取槽位。
4. 必要槽位缺失时返回 `clarify` 或 `next_action=collect_input`。
5. 支持置信度、候选意图、路由原因和低置信度澄清。
6. 支持固定问、规则提示和 LLM 判断协同。
7. 支持 route-only、route-and-invoke、route-and-execute 行为一致。
8. 完成从 `show_plan` 兜底到纯 `plan` 主契约的迁移：多意图返回 `plan` 时，客户端不再依赖 `decision.action=show_plan` 判断是否展示计划；服务端后续兜底生成 Plan 时也不应强制把动作改写为 `show_plan`。
9. 统一用户可见回答字段：新增顶层 `assistant_message` 作为聊天窗口唯一主来源，后端在路由归一化阶段根据路由动作、澄清状态和 Plan 状态生成最终用户可见文案；Agent 调用摘要仍保留在 `AgentInvocationResult.message`，不拼接进普通聊天气泡。前端聊天区优先消费 `assistant_message`，缺失时才兼容回退到 `decision.message`。
10. 收窄现有 message 字段职责：`decision.message` 仅作为路由阶段兼容文案，后续可标记为 deprecated；`next_action.message` 仅作为 Plan / Host 协作提示；`AgentInvocationResult.message` 仅作为 Agent 执行摘要；`decision.reason` 只用于 Route / Debug，不进入普通聊天区。
11. 候选 Agent 和意图粗筛首版保留标签/语义观察信号，不引入向量召回、embedding 检索或额外语义粗排，也不提供重新启用标签裁剪的配置开关。

### 10.4 测试重点

1. 候选 Agent 筛选发生在 LLM 输入前。
2. 传给 LLM 的候选列表只包含当前用户可用 Agent。
3. 缺少必填输入时返回澄清，不直接调用 Agent。
4. 聊天类子智能体可以通过 Registry 配置进入候选列表。
5. 多意图请求返回 Plan。
6. `decision.action` 不为 `show_plan` 但 `plan` 存在时，客户端仍能正确展示计划。
7. 响应包含 `assistant_message` 时，聊天区只展示 `assistant_message`，不再从 `decision.message`、`next_action.message` 或 `result.message` 拼接气泡。
8. 响应缺少 `assistant_message` 时，旧客户端或测试台可回退展示 `decision.message`，保证兼容。
9. `reason`、`next_action.message`、`AgentInvocationResult.message` 分别进入右侧 Route、Plan、Result / Debug 区域，不进入普通聊天气泡。
10. 标签/语义筛选不裁剪 LLM 候选列表；标签命中时记录 `tag_filter=matched_but_not_applied` 和 `tag_filter_matched_agent_ids`，无命中时记录 `tag_filter=no_match_no_filter`。

## 11. M4：上下文预算与 Context Pack

### 11.1 目标

中控必须控制模型看到什么，而不是把全部历史、全部知识和全部文本直接塞进 LLM。Context Pack 是后续记忆、知识、计划和评估的共同基础。

### 11.2 通用概念

| 概念 | 说明 |
| --- | --- |
| Context Budget | 一次路由或执行允许注入模型的最大 token 预算 |
| Context Pack | 进入 LLM 的结构化上下文包 |
| Context Item | 一条候选上下文，例如消息、事件、结果、记忆、证据 |
| Priority | 上下文优先级 |
| Compression | 对长文本、长会话或长结果做摘要或裁剪 |

### 11.3 默认优先级

1. 当前用户输入。
2. 当前场景和当前 Agent 状态。
3. 当前任务 Plan 和未完成步骤。
4. 最近 Agent 结果和用户明确引用的 artifact。
5. 与当前输入相关的 Session / Task / User Memory。
6. 与当前输入相关的 Evidence。
7. 最近会话摘要。
8. 原始历史消息片段。

### 11.4 功能需求

当前实现状态：M4 首版已落地 Context Pack schema、路由前构建、请求级预算覆盖、字符/token 近似换算、单项截断、摘要占位、Route Log 摘要和测试台 Context 标签展示。首版不调用额外 LLM 做摘要压缩；长文本只做截断并记录来源、状态和原因。

1. 定义 Context Pack schema。
2. 将消息、事件、结果、计划、记忆、证据统一转换为 Context Item。
3. 默认使用 token 作为预算单位，支持模型级和请求级预算；场景级预算作为后续扩展。
4. 支持按优先级、相关性、时效性和权限裁剪上下文。
5. 支持对长上下文做摘要压缩。
6. 路由日志记录实际使用和丢弃的 Context Item。
7. UI 右侧调试面板展示 Context Pack。
8. Token 预算估算方式按已确认口径执行：优先使用 LLM Provider 或 API 返回的 token 使用量；如果调用方或 Provider 未返回 token 信息，则使用近似字符换算。
9. 支持“字符上限 ↔ token 预算”换算，用于承接宿主侧只有字符上限、没有 token usage 的环境。
10. 模型 tokenizer 估算可作为后续精度增强项，但不作为 M4 首版默认依赖，避免引入模型绑定和额外依赖复杂度。

### 11.5 测试重点

1. 超预算时低优先级上下文被裁剪。
2. 当前输入和当前任务状态不会被裁掉。
3. 压缩后的上下文保留来源引用。
4. Route Log 能看到上下文使用摘要。
5. 默认预算单位按 token 计算。
6. Provider 返回 token 信息时优先使用真实 token；未返回时使用近似字符换算。
7. 宿主只提供字符上限时，系统能换算为 Context Budget 并执行裁剪。

## 12. M5：用户级、会话级、任务级记忆

### 12.1 目标

把用户之前的对话记忆、任务执行结果和稳定偏好沉淀为可检索、可更新、可审计的通用记忆能力。M5 不是某个 Agent 的私有工具，而是服务中控、Invoker 和后续子智能体的统一平台上下文。

这里使用“用户级记忆”作为通用抽象。特定行业或宿主系统可以把它映射到客户、员工、项目、组织、门店、设备等主体，但核心仓库不内置这些专有字段。

> 命名约定：当前代码中的 `app/repositories/memory.py`、`MemoryMessageRepository` 等表示 in-memory 存储实现，不等同于本模块规划的长期“记忆”能力。M5 使用 `MemoryService`、`MemoryItemRepository`、`memory_context` 等命名表达业务记忆能力，避免和临时内存仓储概念混淆。

Agent Definition 通过 `context.memory` 声明需要的记忆 scope 和执行模式。目标 Agent 接收稳定的 `memory_context` 字段，不需要知道底层是 mem0、Milvus、PostgreSQL 还是后续 adapter。

### 12.2 记忆类型

| 类型 | 生命周期 | 用途 |
| --- | --- | --- |
| Session Memory | 单次会话内 | 支持追问、省略、继续当前 Agent、引用刚才结果 |
| Task Memory | 一个任务或 Plan 内 | 记录任务目标、步骤、输入、输出和阻塞点 |
| User Memory | 跨会话 | 记录用户偏好、常用需求、历史选择和稳定事实 |
| Artifact Memory | 跨任务或跨会话 | 记录生成物、文件、版本和引用关系 |
| Summary Memory | 可滚动更新 | 压缩长会话或长期交互，降低上下文成本 |

### 12.3 记忆数据结构建议

记忆项建议包含：

1. `memory_id`
2. `scope`
3. `subject_type`
4. `subject_id`
5. `content`
6. `structured_value`
7. `source`
8. `confidence`
9. `importance`
10. `ttl`
11. `visibility`
12. `created_at` / `updated_at`

### 12.4 功能需求

1. 支持从消息、Agent Result、Plan Result 中提取候选记忆。
2. 支持写入前策略判断，并提供默认可配置框架：
   - 倾向记录：用户显式偏好、被用户确认的稳定事实、任务结论与产出引用。
   - 倾向不记：闲聊寒暄、未经确认的模型推测、一次性临时值、含敏感信息且未脱敏的内容。
   - 每条候选记忆带 `source`、`confidence`、`importance`，低置信或低重要度内容默认不进入长期记忆。
3. 支持租户/宿主选择开启或关闭记忆；项目本地开发默认开启，但写入必须低风险。
4. 记忆写入默认不在普通聊天中逐条弹窗确认，但必须在调试/管理视图可见。
5. 支持按用户、会话、任务、场景检索记忆。
6. 支持记忆更新、合并、过期和删除。
7. 支持记忆进入 Context Pack 前的权限、时效和相关性过滤。
8. 支持宿主应用提供外部 profile 或历史数据作为只读记忆源。
9. 用户查看和修改记忆的能力应放在核心 API 中；测试台只负责调用 API 并展示前端交互。
10. 当前输入控制当前轮执行，但不能直接改写长期记忆；与长期记忆冲突时记录 session override/conflict。
11. mem0 可作为默认记忆策略层，负责 extraction、semantic search、merge/update；OIR 仍负责租户启用、scope、TTL、权限、脱敏、审计和 Agent 可见性。

### 12.5 测试重点

1. Session Memory 能支持同一会话内追问。
2. Task Memory 能记录 Plan 步骤和结果。
3. 用户/稳定事实记忆由租户/宿主开关控制；本地开发默认开启但写入必须低风险。
4. 无权限用户不能检索其他主体记忆。
5. 被记忆召回的内容能在 Route Log 中追踪。
6. 用户可以查看和修改已写入的可见记忆。
7. 测试台不直接管理记忆存储，只验证核心 API 的展示和修改链路。

## 13. M6：Knowledge Source 与 Evidence 调度

### 13.1 目标

把“动态调用对应知识库”抽象为通用 Knowledge Source / Evidence Provider 调度能力。中控不绑定某个专有文档平台，但本地开发标准基础设施使用 PostgreSQL 保存元数据/日志、Milvus 保存向量，后续可替换 adapter。

M6 分两条路径：

1. 路由阶段 Evidence Provider：为意图识别提供固定问、弱提示或证据片段。
2. Agent 执行阶段 Knowledge Context：按 Agent Definition 的 `context.knowledge` 配置预取或通过固定 workflow node 控制检索，传给 Agent 的字段为 `knowledge_context`。

### 13.2 当前基础

MVP 已有 Evidence Provider 接口，可以返回：

1. `intent_hint`
2. `candidate_agent_ids`
3. `route_override`
4. `evidence`

### 13.3 功能需求

1. 支持注册多个 Evidence Provider。
2. 支持为 Evidence Provider 配置适用场景、适用意图、权限要求和优先级。
3. 支持路由前判断是否需要检索证据。
4. 支持根据用户输入和候选 Agent 选择一个或多个 Provider；场景条件作为后续扩展。
5. 支持证据片段的分数、来源、更新时间和引用信息。
6. 支持证据进入 Context Pack 前的预算控制和去重。
7. 支持固定问强命中、弱意图提示和普通检索证据共存。
8. 支持知识未命中时返回澄清、降级路由或普通 Agent 路由。
9. 支持 Route Log 追踪 Provider 选择过程。
10. 多个 Provider 返回的证据或提示存在冲突时，可以将候选证据传入模型，由模型判断采用哪部分证据以及原因。
11. `/knowledge/search` 是通用治理接口，不强绑定 Agent ID；调用方通过 `caller_type`、可选 `caller_id` 和 `purpose` 表达来源。
12. Agent Definition 中的 `source_ids` 是请求来源，不是授权证明；KnowledgeService 按 source policy 决定 selected/denied。
13. `context.knowledge.mode=prefetch` 才会执行知识预取；默认 disabled。`controlled_retrieval` 只允许固定模板和白名单变量。
14. 固定问归入 M6，但只做“问题到意图/路由”映射，不做固定答案绕过。

### 13.4 Evidence 检索预算控制

Agent 候选数量通常可以通过 Registry 和权限策略控制在较小范围内，真正容易突破模型输入上限的是 Knowledge Source / Playbook / Script 等证据片段。因此 Evidence 进入模型前必须经过 M4 Context Budget 的统一预算裁剪。

```text
用户输入 + 意图 + 候选 Agent
  -> Evidence Provider 检索（固定问 / RAG / 多源）
  -> 证据片段按分数和策略排序
  -> 受 M4 Context Budget 裁剪（Top-K + token 预算）
  -> 进入 LLM 的 Evidence 区
```

功能要求：

1. Evidence Provider 返回的普通证据片段必须包含分数或相关性信息，用于排序和裁剪。
2. 证据片段总 token 受 Context Budget 中 Evidence 区配额约束；超限时按分数、优先级、时效性和权限裁剪低价值片段。
3. 裁剪过程写入 Route Log，记录保留、丢弃和降级原因。
4. 证据检索为空时不阻塞路由，降级为无证据的普通 Agent 路由。
5. 宿主侧如有字符上限硬约束，通过 M4 的字符上限与 token 预算换算统一承接。
6. 固定问强命中走 `route_override` 或强提示路径，不受普通证据片段预算裁剪影响，但仍必须遵守候选 Agent 和权限边界。

### 13.5 暂不进入核心

以下能力暂不进入核心：

1. 文件上传和解析。
2. 向量索引构建。
3. 知识库权限管理后台。
4. 专有文档系统同步。
5. 行业术语库和私有规则库。
6. 未明确边界的 RAG 插件示例。

### 13.6 测试重点

1. 固定问强命中时可以覆盖普通 LLM 路由。
2. 强命中的目标 Agent 仍必须在候选集内。
3. 多 Provider 时按策略选择或合并证据。
4. Evidence 超预算时可裁剪并记录原因。
5. Provider 失败时不影响基础路由可用性。
6. 多 Provider 冲突时，模型可基于证据内容、分数、来源和当前输入进行判断。
7. 暂不要求新增 `selected_evidence_ids` 或 `evidence_reason` 等结构化输出字段。
8. 证据片段总量超预算时，高分片段保留、低分片段被裁剪。
9. 固定问强命中不受普通证据预算裁剪影响。
10. 无证据命中时路由正常工作，不报错。

## 14. M7：Plan 编排与执行协作增强

### 14.1 目标

让中控把复合任务拆成可解释、可确认、可执行、可暂停和可恢复的计划，并在后端可控范围内推进执行。

### 14.2 当前基础

当前已有：

1. `plan` 作为多意图主契约。
2. `execution_policy` 表达执行策略。
3. `next_action` 表达 Host 协作动作。
4. PlanExecutor 复用 InvocationService 执行步骤。

### 14.3 功能需求

1. Plan 步骤记录输入来源：用户输入、历史结果、记忆、证据或上一步输出。
2. Plan 步骤记录可执行性：后端可执行、需要 Host UI、需要用户补充、等待外部事件。
3. 缺少输入时暂停并返回 `next_action=collect_input`。
4. UI Agent 时暂停并返回 `next_action=open_ui`。
5. 长任务时支持等待事件回流。
6. Plan 完成后生成结果摘要，并可进入 Task Memory。
7. Plan 支持状态审计和回放。
8. Plan 某步失败时，必须标记该步为 `failed`，按 `depends_on` 阻塞下游步骤而不是整体静默失败；失败原因回流到 Run / Result，并通过 `next_action` 交回宿主决定重试、跳过或取消，不得把失败步骤伪装成已完成。

### 14.4 测试重点

1. `require_confirmation` 不会自动执行。
2. `auto_execute` 只在允许环境和安全策略下执行。
3. UI Handoff 步骤会暂停，不伪装成已完成外部执行。
4. 缺少输入时返回 collect_input。
5. Plan 执行结果能写入 Agent Result 和 Task Memory。
6. 中间步骤失败时，依赖它的后续步骤被阻塞，已完成步骤结果保留且可追溯。

## 15. M8：可观测性、评估与回放

### 15.1 目标

让开发者和接入方看懂中控为什么这么判断、用了哪些上下文、命中了哪些记忆和证据、为什么需要追问或交接。

### 15.2 功能需求

1. Route Log 记录候选 Agent、最终决策、置信度、原因和校验结果。
2. 记录 Context Pack 的组成、预算使用、裁剪原因和压缩摘要。
3. 记录 Memory 检索、使用和写入结果。
4. 记录 Evidence Provider 调用、命中、失败和降级。
5. 支持基于历史 Route Log 回放。
6. 构建意图回归测试集与评估报告：起步阶段先沉淀标注样例，覆盖单意图、多意图、追问、切换、退出和不支持；样例数量、标注格式和评估报告模板暂不在当前阶段定义，等进入 M8 开发阶段再展开。
7. 测试台右侧展示 Context、Memory、Evidence、Plan、Invocation 链路。
8. 支持导出单次路由诊断包。

### 15.3 数据与隐私边界

1. Route Log、记忆和证据落盘前应对敏感字段脱敏；M5/M6 前新增独立安全模块统一承接脱敏字段清单、脱敏策略和跨主体隔离，不把这些能力继续堆在 `app/core/redaction.py` 中。
2. 记忆与证据严格按 `subject`、用户、租户或宿主侧权限主体隔离，无权限主体不可跨主体检索。
3. 记忆支持 TTL、过期与删除，满足数据生命周期要求。
4. 诊断包导出默认剔除密钥、调用凭证和未脱敏敏感数据。
5. 测试集和回放样例不得包含真实私有数据；如需保留真实结构，应先做匿名化或构造等价样例。

### 15.4 测试重点

1. 每次路由都有可追踪 request_id。
2. Route Log 不泄露密钥和敏感调用配置。
3. 回放同一条样例能得到可比较结果。
4. 评估报告能统计命中率、低置信度、澄清率和错误率。
5. 诊断包导出不包含密钥、token 和未脱敏敏感字段。

## 16. 模块版本规划

后续版本不按一个大版本混合推进，而是按模块建立独立 change。每个模块可以独立开发、测试、验收和合并。

| 模块版本 | 模块 | 建议优先级 | 主要交付 | 是否改后端 | 是否改前端 | 测试口径 |

## 17. 已确认设计决策

以下事项已确认，可作为后续模块设计和 OpenSpec 拆分依据：

1. M1 前端测试台布局方向确认：中间是正常聊天窗口，右侧是统一状态面板。
2. M1 只做测试台 UI，不改后端 API。
3. 聊天窗口中的助手气泡展示中控当前返回给用户的回答，M1 阶段固定使用当前 `decision.message`，不新增后端字段。
4. 右侧状态面板需要分 Tab：Route、Plan、Context、Memory、Evidence、Debug，并默认先展示 Route 和 Plan。
5. 聊天类子智能体应作为可配置 Agent / Intent 进入 Registry，但当前不新增独立聊天 Invoker。
6. 目标 Agent 以路由前候选筛选为主。
7. 后续规划按模块拆分，而不是按 v0.2、v0.3、v0.4 混合多个能力。
8. 近期优先做 M1、M3、M4，再进入 Memory 和 Evidence。
9. 场景级筛选只作为可扩展功能项记录，不作为近期开发要求。
10. mem0 和 RAG-Anything 只作为 adapter 边界规划；本 change 中 mem0 是可选策略层，RAG-Anything 不进入核心依赖。
11. Context Budget 默认单位使用 token。
12. 当前输入控制本轮执行，但不能直接改写长期记忆；冲突记录为 session override/conflict。
13. 记忆写入不需要用户逐条确认，但必须低风险，并支持调试/管理视图查看和修改。
14. 多 Evidence Provider 冲突时，可以把候选证据传入模型，由模型进行判断。
15. token 估算优先使用 LLM Provider 或 API 返回值；没有返回时使用近似字符换算；模型 tokenizer 估算仅作为后续可选增强项。
16. 用户查看和修改记忆的能力放在核心 API，测试台只负责前端展示。
17. Evidence 冲突判断暂不新增 `selected_evidence_ids` 或 `evidence_reason` 字段。
18. M4 是 M5 记忆和 M6 证据进入模型的前置基础，记忆与证据统一经 Context Pack 入模型。
19. M3 需要迁移 `show_plan` 兼容兜底，客户端应以 `plan != null` 作为计划展示主判断。
20. 用户可见回答统一演进路径已确认：M1 用 `decision.message` 过渡，M3 新增 `assistant_message` 作为聊天区唯一主来源，`decision.message` 后续降级为兼容字段。
21. 候选 Agent 和意图粗筛首版只保留标签/语义观察信号，不裁剪候选集，不引入向量召回或额外语义粗排。
22. `assistant_message` 首版采用纯字符串字段。
23. 记忆与证据安全能力新增独立安全模块承接，不继续扩展为 `redaction.py` 单点能力。
24. 固定问归入 M6 Evidence Provider，但保留强固定问的确定性路由特殊地位，只做问题到意图/路由映射。
25. M6 多 Provider 证据冲突暂不补充结构化选择结果和可解释字段。
26. M8 的样例数量、标注格式和评估报告模板当前阶段不定义，进入 M8 开发阶段再展开。

## 18. 已细化实现口径

以下事项已根据人工反馈细化，后续进入模块设计时按此口径展开：

1. `decision.message` 当前是路由器返回给客户端的可展示文案，M1 固定用它作为聊天窗口中的中控回答来源；M3 新增顶层 `assistant_message` 作为统一用户可见回答字段，前端聊天区正常情况下只消费 `assistant_message`，缺失时才兼容回退到 `decision.message`。
2. 右侧 Tab 默认优先展示 Route 和 Plan，Context、Memory、Evidence、Debug 作为可切换调试信息。
3. 推荐 metadata 模板用于规范聊天类 Agent 的扩展配置 key，方便测试台、文档示例、Adapter 和私有接入方一致解析；它不是新的核心 schema 字段。
4. token 预算优先使用 LLM Provider 或 API 返回的 token 信息；没有返回时使用近似字符换算，并支持字符上限与 token 预算换算。
5. 记忆查看和修改属于核心 API 能力；测试台只负责在调试/管理视图展示交互，普通聊天不出现自动写入提示。
6. 多 Evidence Provider 冲突时，把候选证据传入模型判断即可，暂不要求新增结构化选择字段。
7. `next_action.message`、`AgentInvocationResult.message`、`decision.reason` 保留各自职责，分别展示在右侧 Plan、Result / Debug、Route / Debug 区域，不作为聊天区主文案来源。
8. 候选 Agent 和意图粗筛首版采用标签/语义观察信号；标签字段约定可在 Agent 配置、trigger、capabilities 或 metadata 中统一收敛，但当前不用于裁剪候选集。
9. `assistant_message` 首版为 `string`，后续只有在需要多类型展示、来源追踪或多段消息时，才考虑升级为结构化对象。
10. 安全模块独立设计，统一负责敏感字段清单、脱敏策略、诊断包导出过滤和跨主体隔离检查。
11. Agent 不自由调用记忆/知识检索；由 Agent Definition 的 context 配置驱动 prefetch 或固定 workflow node controlled retrieval，再以 `memory_context`、`knowledge_context` 传入。

## 20. 阶段性结论
