# 中控系统对齐会议纪要与后续工作清单

## 1. 背景

本次会议围绕 `open-intent-router` 中控系统与公司内部子牙系统的接入可行性进行对齐。现有交付说明中，中控系统定位为从「意图识别器」升级到「智能体编排中枢」：用户输入先经过中控完成权限过滤、固定问命中、LLM 意图识别、多意图计划生成，再由子牙系统根据中控返回结果执行打开 Agent、继续当前 Agent、退出 Agent、展示追问、展示计划或回传执行状态。

会议结论整体偏正向：内部研发侧认可该方向具备接入和测试价值，但需要进一步明确研发协作模式、需求管理流程、内网模型验证、意图体系分层、上下文记忆、模型蒸馏和生产级接入边界。

## 2. 会议核心结论

### 2.2 接入可行性

研发侧初步判断方向上没有明显问题，可以考虑接入内网进行部署和测试。但正式推进前，需要评估两个方案后进入需求管理或研发迭代流程，并明确双方协作方式。

1. 两边方案评估和选择
2. 联合开发方式：由中控系统作者与内部研发共同推进，节奏更灵活，适合快速验证。
3. 方案移交方式：将方案、接口、代码和说明交由内部研发独立实现或改造，需先评估工作量和排期。

### 2.5 建议蒸馏专用小模型

若方案方向确认，可以基于现有行内大模型能力和历史意图语料，蒸馏一个专门用于意图识别的小模型。

1. 提升意图识别实时链路的执行效率。
2. 降低直接调用大模型的成本和时延。
3. 在特定业务场景下提升分类稳定性和准确率。
4. 为固定业务领域建立更可控的模型能力。

内部平台已具备模型蒸馏能力，已有相关 Demo，可作为后续验证方向。

## 3. 接下来工作清单

### P0：推进立项与接入验证

1. 明确中控系统接入子牙的协作模式：联合开发还是方案移交。
2. 确认是否需要进入需求管理流程，以及对应需求编号、负责人、迭代窗口和验收方式。
3. 与内部研发确认第一阶段内网部署环境：开发、测试或沙箱环境。
4. 将当前外网 Demo 部署到内网可访问环境，完成基础启动和连通性验证。
5. 确认子牙侧调用中控的主接口仍以 `POST /api/v1/route` 为主链路。
6. 确认子牙侧需要传入的用户字段、角色字段、组织字段、租户字段和业务权限字段。
7. 梳理第一批试点 Agent / Tool / Workflow 清单，并映射成中控 Agent Definition。
8. 明确固定问、页面跳转、知识库检索、Agent 调用结果回传的第一版接口边界。

### P0：内网模型验证

1. 在内网模型上验证单意图识别效果。
2. 在内网模型上验证多意图识别和计划生成效果。
3. 对比内网小参数模型、大参数模型在准确率、时延、稳定性上的差异。
4. 建立最小验证集，覆盖单意图、多意图、固定问、无命中兜底、权限过滤、上下文切换等场景。
5. 输出内网模型验证报告，明确是否可以直接用于第一阶段试点。
6. 若直接使用大模型时延不可接受，启动意图识别专用小模型蒸馏方案评估。

### P0：意图体系与接入边界

1. 确认是否采用分层意图体系：主场景 -> 业务意图 -> Agent / Tool / Workflow。
2. 确认中控负责到哪一层，哪些细分判断交给业务域或子 Agent 自行处理。
3. 建立 Agent 注册规范，包括 Agent ID、名称、描述、权限、标签、输入输出、调用方式、页面跳转信息等。
4. 明确权限过滤是硬边界，标签和语义筛选作为候选召回或排序依据。
5. 明确多意图计划是否只支持同一业务域内编排，还是允许跨业务域编排。
6. 对跨业务域计划增加用户确认、失败中断、回滚或人工接管策略。

### P1：上下文、记忆和压缩

1. 设计 Context Pack 模块，统一管理当前输入、短期上下文、长期记忆、Evidence、工具结果和 Agent 摘要。
2. 增加上下文预算策略，控制进入模型的内容长度、优先级和压缩方式。
3. 优先实现 Session / Task Memory，支持当前任务内的上下文延续。
4. 再评估 User Memory，支持用户长期偏好、历史行为和常用业务场景召回。
5. 对工具调用记录和历史 Agent 回复进行摘要压缩，避免长上下文堆叠。
6. 增加记忆权限隔离和脱敏策略，避免跨用户、跨租户、跨业务域污染。

### P1：蒸馏小模型方案

1. 与内部大模型平台确认蒸馏流程、数据格式、训练资源、上线方式和调用接口。
2. 收集历史意图语料，包括用户真实问法、命中意图、兜底样例、多意图样例和歧义样例。
3. 制定标注规范，区分主场景、业务意图、Agent、固定问和多意图计划。
4. 用现有大模型辅助生成或清洗训练样本。
5. 训练意图识别专用小模型，并与通用大模型进行效果和时延对比。
6. 设计混合路由策略：固定问优先，小模型快速分类，大模型处理复杂多意图或低置信度场景。

### P1：评估、回放和监控

1. 建立标准化测试集，覆盖核心业务场景和边界样例。
2. 增加路由准确率、Top-K 命中率、多意图计划准确率、兜底率、澄清率等指标。
3. 建立 Route Log 回放能力，用于回归测试和模型迭代对比。
4. 增加响应时延、模型耗时、候选数量、Token 消耗、Plan 执行成功率等监控指标。
5. 建立错误样本沉淀机制，用于后续语料标注和模型蒸馏。

### P2：生产化能力补齐

1. 完善日志脱敏、审计、数据生命周期和访问控制。
2. 设计故障降级策略：模型不可用、Agent 不可用、知识库不可用、计划执行失败等情况。
3. 完善 Plan 状态机，包括 pending、running、blocked、completed、failed、cancelled。
4. 补充 Agent Event 协议，规范进度、结果、失败、阻塞、摘要等回传格式。
5. 明确正式 UI 由子牙承载，中控测试台仅用于演示和联调。
6. 完善部署文档、接口文档、联调手册和验收说明。

## 4. 需要沟通内容

### 4.1 项目方向确认

> 当前方案不是替代子牙现有 Agent，而是在用户输入和各 Agent 能力之间增加统一路由、权限过滤、多意图计划和执行状态编排能力。短期目标是完成内网接入验证，长期目标是沉淀统一的智能体调度中枢。

### 4.2 研发协作模式

1. 是否由当前项目作者与内部研发联合推进。
2. 是否需要正式纳入需求管理流程。
3. 第一阶段由哪个团队牵头、哪个团队配合。
4. 内部研发投入多少人力评估、接入和改造。
5. 目标进入哪个月度或双月迭代。

### 4.3 第一阶段试点范围

需要领导协调业务和研发一起确定第一批试点范围：

1. 第一批接入哪些 Agent / Tool / Workflow。
2. 是否优先选择 O 端整体意图合并相关场景。
3. 是否覆盖系统指引、话术生成、访前准备、知识问答等典型场景。
4. 验收问题集由谁提供、谁确认通过标准。
5. 多意图场景是否纳入第一阶段验收，还是作为第二阶段增强。

建议第一阶段范围不要过大，应覆盖单意图、固定问、权限过滤和一到两个多意图样例即可。

### 4.4 内网模型与算力资源

需要领导协调大模型平台或相关团队：

1. 提供内网模型调用权限和测试环境。
2. 明确实时链路可用模型、并发、限流和 SLA。
3. 明确离线算力或夜间算力是否可用于语料处理和模型蒸馏。
4. 确认是否支持意图识别专用小模型训练、部署和调用。
5. 若需要蒸馏模型，确认语料准备、数据合规、训练审批和上线流程。

建议将“内网模型效果和性能验证”作为第一阶段关键里程碑，否则外网 Demo 的效果无法直接证明生产可行性。

### 4.5 数据与权限边界

需要领导推动明确：

1. 用户身份、角色、组织、租户、权限字段由哪个系统提供。
2. Agent 权限和业务域权限由谁维护。
3. 知识库 Evidence 是否有现成 HTTP 检索接口。
4. 长期记忆是否允许建设，数据保存周期和脱敏规则是什么。
5. Route Log、模型输入输出、Agent 执行结果是否可以落库用于评估和回放。

这些内容直接影响中控是否能从 Demo 走向生产可用。

### 4.6 风险和决策点

需要提前向领导说明的主要风险：

1. 内网模型能力与外网模型存在差距，多意图计划效果需要重新验证。
2. 大模型实时调用可能存在时延和并发风险。
3. 如果不做意图分层，中控可能难以兜住所有业务域细分逻辑。
4. 如果缺少标准测试集，后续很难评估准确率和迭代收益。
5. 如果缺少用户确认机制，多意图自动执行容易造成误操作风险。
6. 如果没有明确协作模式，项目容易停留在 Demo 和方案讨论阶段。

建议领导优先拍板三个事项：

1. 是否进入内网试点。
2. 采用联合开发还是研发独立承接。
3. 第一阶段试点范围和验收标准。
